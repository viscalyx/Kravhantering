Throwaway logic prototype

Minimal Azure Dev start and stop

This demo asks whether the smallest concrete orchestration feels right: exact targeted Azure CLI calls, a short local lock, visible progress, stable results, and explicit failure boundaries—without SSH readiness or trust repair in the lifecycle commands.

Assumptions held fixed: configuration has already been parsed and validated; the configured SSH alias already exists; setup repairs changed SSH trust. The separate configuration boundary, final -WhatIf contract, and strictness of the local audit-log write remain decisions to make after reacting to this flow.

    What this candidate is asserting

    • The lock covers only session repair, the decisive state read, and mutation submission. Polling happens without the lock.
    • Every Azure operation names subscription, resource group, and VM; there is no az account set or subscription enumeration.
    • start waits only for Azure to report PowerState/running, then prints existing SSH and VS Code entry points. It does not touch SSH files or test SSH.
    • stop returns as soon as asynchronous deallocation is accepted. It never waits for the VM to become deallocated.
    • One terminal local log record is shown as a candidate boundary after lock release. Whether its failure is fatal or warning-only is not settled by this prototype.
